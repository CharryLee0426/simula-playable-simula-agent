# Simula Playable Simulation Agent（中文说明）

给它任何一个没见过的 HTML5 playable：它在手机尺寸的浏览器里加载游戏，从画面上自己弄懂玩法，像真人一样玩，
以 30 fps 录下每一帧（带游戏原声），剪出一支 20 秒 9:16 的高光视频，写出新手 friction 报告，并给自己的成片打分。

```bash
./run --playable ./game.html --out highlight.mp4
```

没有任何 per-game 代码、规则或坐标：游戏相关的一切都在运行时从像素、DOM（如果有）和游戏注册的输入事件中得到。

## 核心设计

1. **虚拟时钟，而不是实时。** 注入的 shim 接管游戏能读到的所有时钟（rAF、定时器、performance.now、Date、
   event.timeStamp、CSS/Web Animations、AudioContext.currentTime），游戏只在 agent “推进一帧”时前进。
   模型思考时游戏冻结，思考时间不会出现在画面里；每一帧之间严格相隔 1/30 秒游戏时间，与机器快慢无关
   （无 GPU 时 3D 样例实时只有 2–5 fps，实时录制根本做不到 30 fps）。两个通用护栏：忙等循环检测
   （启动时的 CPU 跑分）和显式结束 Web Animations（否则 `.finished` 回调不触发、特效会冻在屏幕上）。
   按实时完成的工作也钉在游戏帧上：解码图片（`createImageBitmap`、`img.decode()`、`<img>` 的 load/error）、读取
   `data:`/`blob:` URL 和 Blob（`fetch`、`Response`/`Blob` 的 body）、字体、`<script src>` 加载和 `decodeAudioData`
   在请求时被记录；每一步在它的同步点上（按实时）等到已请求的工作全部完成，结果（promise、load/error 事件、回调）
   按请求顺序由虚拟定时器在下一帧开头送达，一条链（fetch → blob → `createImageBitmap`）在任何机器上都是每环一帧。
   `KHR_parallel_shader_compile` 第一次查询就报告编译完成。步进前发出的输入在这一帧之前处理：Chrome 在某个真实渲染帧
   才把触摸移动交给页面，3D 页面上可能比 CDP 调用返回晚 250 ms，所以页面统计收到的输入、worker 统计发出的输入，
   步进先等两者一致。游戏自己卡住的工作最多等 10 秒，之后在完成时送达；`import()` 加载的模块无法拦截，到达时即运行。
2. **由浏览器按游戏时间渲染游戏音频。** 游戏拿到的 `AudioContext` 其实是一个以虚拟时钟为 `currentTime` 的
   `OfflineAudioContext`：游戏排进音频时间线的一切（`start`/`stop`、音量包络、滤波和音高扫频）直接交给 Chromium
   的音频引擎；实时上下文会立即生效的操作（`connect`/`disconnect`、`.value =`、正在发声节点的属性）记下游戏时间，
   在渲染时于对应时刻重放。会话结束时 Chromium 一次性渲染整段音频，压缩器、滤波器、包络与玩家听到的完全一致；
   `<audio>` 元素照旧记录播放/暂停/音量后混音，和视频逐帧同步。旧版本在 Python 里按事件日志重新合成 Web Audio：
   只在声音开始时读一次增益（包络尚未生效，通常读到 1.0），并丢掉滤波和扫频，于是合成音效变成又响又平的方波/锯齿波
   “8 位”蜂鸣，比音乐高出最多 28 dB。该路径保留为 `audio: "log"` 备用；已交付视频的音频由 `python -m simbrowser.remix`
   通过逐帧验证过的会话重放重新生成。
3. **像玩家一样看，加上通用辅助。** 主观察是截图；DOM 游戏额外给可交互元素画编号（set-of-marks），
   并告诉规划器游戏监听了哪些输入事件（能不能拖拽）。从不读取游戏内部变量。
4. **慢而聪明的规划器 + 快而便宜的判断。** 规划器（Gemini 4 Hydrogen）每回合看截图、写笔记、给出 1–4 个手势；
   Decider（Perplexity Decider，Decisions API，约 0.3 秒、免费）在同一冻结帧上回答类型化问题：屏幕阶段、
   上一个输入是否生效（前后两张图）、新手是否知道下一步做什么、画面刺激程度。
5. **像人的手。** 对数正态反应时间 + 画面大变后的阅读时间、Fitts 定律、贝塞尔曲线拖拽 + 抖动、按压持续几帧、
   偶尔点偏（“熟练但不完美”）。高光视频里按动作日志画出手机式触摸指示，让观众一眼看懂核心玩法。
6. **模型决定故事，代码保证数字。** Director 写三份不同策略的剪辑表（EDL）；代码保证严格 20.0 秒、
   速度 1.0–1.5×、素材 ≤ 30 秒、不在手势中途切、去掉死画面（保留约 1 秒自然停顿）、结尾是 end card。
7. **多候选 + 评估 + 对照组。** 规格门槛 + 可解释启发式 + VLM 评审 + 两两比较；两个“偷懒剪法”
   （前 20 秒、随机片段）用同样方式打分，评估必须把它们明显排在真实剪辑之下。
8. **end card 是广告的一部分。** 停留 2.5 秒后点一次 CTA；剪辑以它结尾。
9. **快反应游戏的“大脑 + 脊髓”。** 跑酷、躲避类游戏里，一张截图一次决策太慢。规划器改为写一个 reflex policy：
   一个注意力区域（玩家正前方的一条区域，“在区域内”就等于“很近了”）+ 2–5 个情境及对应手势（例如“车道里有粉色方块、
   左边车道空 → 左滑”，“横跨所有车道的橙色栏杆 → 上滑跳”）。执行器每 0.1 秒游戏时间让 Decider 判断当前是哪个情境，
   以人类反射时间（约 210 ms，偶尔慢半拍）触发手势，变道后短暂“认定”不来回摇摆；每 0.5 秒看一次全屏，崩溃/弹窗或
   **策略没覆盖的新东西**（新障碍、新教程提示、道具）出现就交还给规划器。规划器只在游戏真的太快时才升级到 reflex
   （跑酷类）；较慢的躲避游戏里逐回合精确操作不比 reflex 差（对照实验见英文 README）。
   注意力区域**跟着玩家走**：规划器指出它控制的对象在哪，worker 用模板匹配（归一化互相关，numpy，几毫秒）逐帧跟踪，
   区域随玩家位移移动，Decider 看到的永远是以玩家为中心的裁剪图（“玩家左边”= 图的左边）。墙是学出来的：一个本该
   让玩家横移的反射没让（高置信度跟踪下）位置变化，就是撞墙了，1.5 秒内改走另一个方向。
   区域**看多远是从被撞中学出来的**（`src/agent/zone.ts`）：worker 在录下的帧里找两种通用的撞击特征——**闪光**（画面变化
   突然飙升且亮度跳升，游戏表现撞击的闪光/震屏）和**定格**（一直在动的画面突然停住，崩溃弹窗让世界暂停）。吃道具也会闪、
   教程提示也会暂停，所以再用一次 Decider 全屏提问确认（“是被撞/坠毁，不是吃道具或教程暂停？”）；每 0.5 秒的全屏检查也问
   同一个问题，抓住两种特征都漏掉的撞击，并由 worker 从上次检查以来的帧里推算撞击时刻。确认的定格会立刻结束策略（视频里
   不留定格的死画面）。然后看撞之前最后一次反应的提前量：不到 0.5 秒（或根本没识别出危险）→ 看见得太晚，区域远端往外扩 15%；
   超过 1.2 秒 → 反应太早（跳早了落在栏杆前），远端往回收；介于之间说明是反应本身错了，为了吃道具（情境标
   `"pickup": true`）撞上障碍是判断失误——这两种都不改深度，而是告诉规划器去改情境。远端是玩家对面那一侧（跑酷是上方，
   横版是右侧）；调整在整个 session 里保留，因为游戏速度会延续到下一个策略。每次被撞、证据截图和深度变化都记在
   `reflexes.jsonl` 和 `trace.html` 里。

## 编排与可追溯性

每个 playable 是一个 Pi Durable `SessionTask`：play → index → cut → render → eval → friction → report，
每个阶段提交 checkpoint，崩溃或 Ctrl-C 后从断点继续；`--redo <phase>` 可以不重玩直接重剪/重评。
每个 session 目录里有：`trace.html`（整个会话逐回合：看到了什么、笔记、动作、Decider 判断、成本，点击时间跳转原始录像）、
`plans.jsonl`、`actions.jsonl`（逐帧手势）、`observations.jsonl`、`ledger.jsonl`（每次付费调用）、`trace.jsonl` 等。
